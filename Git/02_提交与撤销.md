# Git 提交与撤销

返回 [Git 学习索引](00_Git学习索引.md)。提交前后的操作很容易混淆，关键是先分清改动位于工作区、暂存区还是提交历史。

## 创建清晰的提交

```bash
# 精确暂存指定文件（比 git add . 更容易复核）
git add src/login.ts README.md

# 核对将提交的内容
git diff --staged

# 提交信息通常采用：type: 简短说明
git commit -m "fix: handle expired session"
```

常见 `type`：`feat`（功能）、`fix`（修复）、`docs`（文档）、`refactor`（重构）、`test`（测试）、`chore`（杂项）。团队已有约定时，以团队规范为准。

若刚提交就发现遗漏了一个文件，可以补充到最近一次**尚未推送**的提交：

```bash
git add <遗漏文件>
git commit --amend --no-edit
```

> [!warning] `--amend` 会改写最近一次提交
> 若该提交已推送并可能被其他人基于它开发，先与团队沟通；通常更安全的方式是再创建一个新提交。

## 安全撤销：按位置选择命令

| 目标 | 命令 | 会不会丢弃文件改动 |
| --- | --- | --- |
| 取消暂存，保留文件内容 | `git restore --staged <文件>` | 不会 |
| 丢弃某个未暂存文件的改动 | `git restore <文件>` | 会 |
| 将已提交的修改用新提交抵消 | `git revert <提交ID>` | 不会改写历史 |
| 暂时收起当前工作 | `git stash push -m "说明"` | 不会，改动存入 stash |

使用 `git restore <文件>` 前，先用 `git diff -- <文件>` 核对，因为该操作会覆盖工作区内容。

## `reset`：理解三种模式

`git reset` 会移动当前分支指针，适合处理自己的本地历史。`HEAD~1` 表示最近一次提交的父提交。

| 命令 | 提交历史 | 暂存区 | 工作区 | 适用场景 |
| --- | --- | --- | --- | --- |
| `git reset --soft HEAD~1` | 回退 | 保留 | 保留 | 想重新组织最近一次提交 |
| `git reset --mixed HEAD~1` | 回退 | 清空 | 保留 | 想重新选择暂存内容；默认模式 |
| `git reset --hard HEAD~1` | 回退 | 清空 | 覆盖 | 确定不再需要最近一次提交及其改动 |

> [!danger] 谨慎使用 `git reset --hard`
> 它会覆盖工作区和暂存区。执行前至少运行 `git status` 与 `git diff`；已推送到共享分支的提交优先使用 `git revert`。

## 暂存工作：`stash`

当手头改动尚未完成，但需要切换分支处理紧急任务时：

```bash
# 保存已跟踪文件的改动；-u 同时包含未跟踪文件
git stash push -u -m "wip: checkout refactor"

git stash list
git switch hotfix/urgent

# 回到原分支后恢复，并删除这条 stash
git stash pop
```

如果只想恢复但暂时保留 stash，使用 `git stash apply`。`stash` 是临时工具，不宜长期当作未提交工作的仓库。

## 找回“刚才还在”的提交

分支指针被移动后，可先查看引用日志：

```bash
git reflog
# 找到目标状态后，新建分支保留它
git switch -c rescue-work <提交ID>
```

`reflog` 记录本地引用变动，对误操作后的自救尤其有用；找到目标后立即创建分支或提交，以免记录过期。
